3. Etapa 1: correções essenciais do protótipo (≈½ dia)

Cada item com teste que o proteja:

async def bloqueante: em app/principal.py, classificar é async def, mas a chamada ao Groq usa httpx.post síncrono (até 5 s) e trava o servidor. Troque a rota para def (pool de threads do FastAPI) ou use httpx.AsyncClient. Escolha uma, justifique em 1 linha.
Probabilidades: a árvore rasa devolve proporções de folha, não confiança. Em API e interface, renomeie para "proporção de amostras parecidas" (ou calibre com CalibratedClassifierCV se couber, e então justifique). Nunca rotule como "confiança" ou "certeza".
Fora do que o modelo viu: a API aceita −10 a 60 °C, mas o treino cobre 5 a 42 °C. Defina em config/faixas.json (fonte única de verdade das faixas de treino, das faixas provisórias de rotulagem e dos limites dos controles da interface; gerador de dataset, API e front leem dele) e devolva aviso_fora_da_faixa_de_treino: true quando a entrada sair do treino. Limite os controles deslizantes da interface ao intervalo do treino.
Revocação do Vermelho (hoje 0,809; o README fixa meta ≥ 0,90): implemente uma regra conservadora de decisão (classificar como Vermelho quando P(Vermelho) ≥ limiar). Escolha o limiar em um conjunto de validação (validação cruzada ou split próprio), nunca no conjunto de teste, e só depois reporte no teste. Compare com class_weight. Relate o custo (mais falsos alarmes: precisão do Vermelho e acurácia). Se a meta de 0,90 não for atingida, não force: relate o número real e a discussão do trade-off.
Teto da acurácia: calcule a acurácia da própria regra de rotulagem sem ruído nas features contra os rótulos ruidosos. Isso dá referência honesta ao ~75% e deve aparecer em metricas.json, em avaliacao.html e no README. Frase obrigatória: o ML aqui valida o pipeline, não a eficácia agronômica em campo.
Higiene: treinar.py não deve sobrescrever metricas.json e o dataset a cada execução (flag --salvar ou --forcar); não versionar ARQUIVOS_APOIO/; fixar versões em requirements.txt. Decidir se o modelo.pkl fica versionado agora (sim, até o deploy) e registrar que no deploy ele será gerado no build.

Critério de aceite: pytest -v verde (mostre a saída), métricas regeneradas e coerentes, git status limpo de arquivos indevidos.

Objetivo: demo bonita, convincente e honesta, com muitos dados simulados. Mobile first, contraste alto, alvos de toque ≥ 44 px, foco visível, aria-live na mudança de estado, textos simples. Cores do semáforo só para status; cada estado também com texto + ícone + forma distinta (círculo, triângulo, octógono) para daltonismo.

Arquitetura de dados do simulador: criar uma interface FonteDeLeituras com duas implementações, FonteSimulada (agora) e FonteBanco (Etapa 3). As páginas consomem a API e não sabem qual fonte está ativa.

2.1 Simulador ao vivo (item 2): endpoint GET /simulador/leituras (e/ou SSE) que gera leituras novas a cada 2–3 s por talhão, com passeio aleatório com semente e ciclo do dia (o solo seca com o tempo, a temperatura sobe à tarde, eventos como chuva simulada). Na interface: transição suave do semáforo, "atualizado há X s", controles de pausar/velocidade. Cada leitura passa pelo mesmo /classificar real. Dados e API sempre marcados como simulados.

2.2 Visão geral por talhão (item 3): web/talhoes.html com 6 a 8 pontos de monitoramento dentro de uma única propriedade (por exemplo "Talhão A, Arábica"), em cards ordenados por gravidade (Vermelho primeiro), com filtro por espécie e estado. 2.3 Visão do agricultor (item 4): web/agricultor.html com um semáforo gigante, uma frase curta, botão grande "Ouvir" (Web Speech API, pt-BR, sem serviço externo; se o navegador não suportar, mostrar aviso claro), e link "Ver detalhes" para a visão técnica. 2.5 Leituras em barras com zonas (item 7): componente JS reutilizável (barra_zonas.js) que mostra cada variável como barra com faixas ("Solo: seco / ok / encharcado"; "Temperatura: fria / ok / quente"; "Ar: seco / ok / úmido") e um marcador, com os limites vindos de config/faixas.json e a nota "faixas provisórias". 6. Etapa 4: dados reais do pipeline: persistência, ingestão e gateway (≈4 dias)

Implementa o que o relatório prevê (seções 7.3, 8.2, 8.4) e a FonteBanco.

Persistência: SQLAlchemy com DATABASE_URL (padrão SQLite local; Postgres gerenciado no deploy). Tabela de leituras: id, ponto/talhão, espécie, umidade do solo, temperatura, umidade do ar, instante de coleta, origem (simulado|dispositivo), validade. Migração simples (criação no startup ou Alembic, o que for mais enxuto). Atenção: discos de serviços gratuitos podem ser efêmeros; documente a escolha (banco gerenciado gratuito, conferindo as regras vigentes do serviço no momento) e inclua rotina de semente (seed) para o deploy não ficar vazio.
Ingestão: POST /leituras com token de dispositivo (Authorization: Bearer lido de TOKEN_DISPOSITIVO), validação de formato/faixa, rejeição de requisições malformadas e de campos extras (como já é feito em /classificar), idempotência por (ponto, instante).
Dado desatualizado: regra configurável (ex.: leitura mais antiga que N minutos = "sem dados atualizados", cinza, nunca cor de avaliação). Endpoint de disponibilidade de leituras válidas em 72 h (indicador do relatório, meta ≥ 95%).
Gateway (gateway/gateway.py): PySerial, Pandas e NumPy; lê linhas do Arduino, valida (mensagem incompleta, valor fora de faixa, duplicidade, oscilação abrupta), guarda buffer em SQLite local e envia à API por HTTPS com retentativa e backoff. Protocolo de linha documentado (ex.: S:432;T:27.5;U:61). Modo simulado: como o Arduino não está montado, aceite uma porta virtual (loop:// do PySerial ou um gerador) para demonstrar o pipeline real de ponta a ponta. Todo dado desse modo entra com origem = simulado.
Sketch Arduino (arduino/agroanalise/agroanalise.ino): sensor de umidade do solo + DHT11, saída no protocolo acima. Marcar no README e no próprio arquivo: "não testado em hardware" até alguém montar o circuito; incluir o esquema de ligação em texto e a calibração do sensor de solo como etapa pendente (o relatório trata a calibração como essencial).

Critério de aceite: o gateway no modo simulado alimenta a API, os dados aparecem em painel/talhoes/historico, e o estado "desatualizado" aparece quando o gateway é parado.

8. Etapa 6: avaliação (eval) da IA (≈3 dias) — vale 25%

Classificador (ml/avaliar_classificador.py → docs/avaliacao/classificador.md + .json):
